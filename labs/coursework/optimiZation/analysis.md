# Курсовая — разбор Sokoban перед профилированием

Обновлено 2026-10-22. Код: `Desktop/sokoban` (`github.com/sanueee/sokoban`), C11, ~2600 строк.
Требования: `../Курсовая.docx` (копия — `pl-course/материалы/Курсовая.docx`). Машина замеров: Kali, AMD Ryzen 5 4500U, GCC 15.2.0, valgrind 3.27.1.
Тема с преподавателем **ещё не согласована**.

Это разбор кода «на глаз». Что из этого реально тормозит — покажет профилировщик.
Всё, что ниже помечено «гипотеза», проверяется замером, а не принимается на веру.

> **Проверено профилем 2026-10-22 → `v0/summary.md`.** На easy+medium 63 % — генерация
> (`rand` в цикле попыток `ReverseSolve`), 36 % — решатель (`Heuristic` 13 %). Гипотеза «главное — решатель»
> для easy/medium не подтвердилась; гипотеза про ~44 МБ на каждый вызов решателя — подтвердилась (massif).

> Раздел 6 (команды) частично устарел — актуальные команды в `handoff.md` и `v0/summary.md`.

## 1. Как устроена программа

```
main.c ── главный цикл 60 FPS (raylib): ввод → логика → отрисовка
  ├── ui.c       экраны (меню, логин, история, статистика…); выбор сложности → GenerateLevel
  ├── render.c   рисует поле каждый кадр
  ├── game.c     ход игрока, undo (связный список), проверка победы
  ├── level.c    ГЕНЕРАЦИЯ уровня (лабиринт → цели → обратные ходы → проверка)
  ├── solver.c   A*-РЕШАТЕЛЬ (Ctrl+B)
  └── db.c       SQLite: пользователи и сессии
tests/bench.c   отдельная программа: N уровней × 3 сложности → CSV (без окна)
```

**Что имеет смысл оптимизировать в курсовой:** `solver.c` и `level.c`. Это чистые вычисления,
их измеряет `bench.c`. Отрисовка, музыка и БД ограничены 60 FPS и вводом человека.
Ускорять их бессмысленно: экран всё равно ждёт следующего кадра.

## 2. Найденные проблемы с измерениями (до профилирования)

Совпадает с заметкой напарника.

1. **`srand(time(NULL))` внутри `GenerateLevel`** (`level.c:236`). Seed (начальное значение генератора
   случайных чисел) меняется раз в секунду. Отсюда два следствия:
   - нельзя прогнать «тот же уровень» до и после оптимизации, поэтому сравнение некорректно;
   - **старый `tests_res.csv` почти наверняка измерял одни и те же уровни по много раз.**
     Все генерации в пределах одной секунды получают одинаковый seed и одинаковый уровень. Это видно
     по повторяющимся `0.66 / 0.67` в easy. Значит, старый CSV для отчёта не годится как «исходная версия».
2. **`printf` внутри `SolveLevel`** (`solver.c:683`). Вывод на каждый вызов попадает в замер времени (мелочь, но шум).
3. **`bench.c` пишет в `../tests/bench_results.csv`**, то есть запускать его нужно строго из `build/`.
4. В README размеры полей (8×8…18×18) не совпадают с кодом (9–11, 11–12, 13–14). Для отчёта брать код.

Значит, **первый коммит курсовой — не оптимизация, а подготовка замеров**: seed передаётся
снаружи (или фиксированный набор seed'ов), `bench` повторяем. Решаете завтра вдвоём.

**Горячесть** — сколько раз вызывается:
🔴 внутри цикла A* (на каждый узел, миллионы раз), 🟠 внутри генерации (тысячи раз),
🟢 один раз за уровень или за кадр. `k` — число ящиков (3–8), `F` — свободные клетки поля (до ~150).

## 4. Оценка сложности исходного решателя (черновик для пункта 3 методички)

- **Состояние** = позиция игрока + позиции k ящиков. **Каждый шаг игрока — отдельный узел**,
  даже если ящик не двигался.
- Размер пространства состояний: примерно **F · C(F, k)**. При F≈100, k=7 это ~10¹² теоретически,
  на практике A* с эвристикой обходит малую часть.
- Время: **O(N · (k² + log N))**, где N — число раскрытых узлов. N растёт экспоненциально от
  длины решения и числа ящиков (≈ O(b^d), b ≤ 4).
- Память: O(N): узел ~40 байт + запись в хеше ~22 байта + индекс в куче 4 байта.
  Плюс ~43 МБ выделяется на старте **при любом** уровне.
- Эвристика допустима, поэтому найденный путь кратчайший по числу шагов.

## 5. Идеи оптимизаций — вопросы на завтра, не решение

Методичка требует **1 алгоритмическую** и **≥ 2 машинно-независимых**.
Машинно-независимые — это преобразования кода, которые ускоряют на любом процессоре
(вынос инвариантов, предвычисление, замена дорогих операций, избавление от лишней работы).

**Кандидаты в алгоритмическую:**
- поиск по **толчкам** вместо шагов: узел = расстановка ящиков + область, куда может дойти игрок.
  Пространство уменьшается примерно в F раз;
- **предвычисленные «мёртвые клетки»** (dead squares): один раз на уровень BFS от целей «назад».
  Ящик на такой клетке никогда не попадёт на цель. Отсекает больше, чем угол и 2×2;
- более сильная эвристика (паросочетание ящик↔цель вместо «каждому ближайшую»);
- в генераторе: flood fill не на каждый обратный ход, а инкрементально.

**Кандидаты в машинно-независимые:**
- таблица `x, y` / расстояний вместо `% MAX_FIELD` и `/ MAX_FIELD` в `Heuristic` и `IsDeadState`;
- **битовая карта занятых клеток** вместо `IsBoxAt`/`IsGoal`/`HasBox` — O(1) вместо O(k);
- `SortBoxes`: двигается один ящик, поэтому можно один сдвиг вставкой вместо сортировки всего массива;
- угловые дедлоки — предвычисленная таблица на уровень (стены не меняются, а проверяются на каждом узле);
- убрать выделение ~43 МБ на каждый вызов или стартовать с меньших размеров;
- `f` хранить прямо в куче рядом с индексом, чтобы не ходить в `pool->data` (локальность);
- убрать `printf` из решателя.

Открытые вопросы на завтра:
1. Какая из алгоритмических? Поиск по толчкам меняет «оптимальность»: решение станет кратчайшим
   по толчкам, а не по шагам. Это надо будет оговорить в отчёте.
2. Кто какую оптимизацию коммитит (нужны коммиты от обоих).
3. Фиксированный набор уровней: сколько seed'ов на каждую сложность, будет ли hard.

## 6. Как профилировать (команды запускает пользователь)

Подготовка (один раз):
```bash
sudo apt install cmake libraylib-dev libsqlite3-dev kcachegrind
cd ~/Desktop/sokoban && mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=RelWithDebInfo    # -O2 -g: оптимизации + имена функций в профиле
make sokoban_bench
```

Проверить, что пакет `libraylib-dev` есть в репозитории Kali: `apt-cache policy libraylib-dev`.

**Время по функциям — callgrind** (memcheck без флагов время не меряет):
```bash
valgrind --tool=callgrind --callgrind-out-file=cg_base.out ./sokoban_bench 5
callgrind_annotate --inclusive=yes cg_base.out | head -40   # с учётом вложенных вызовов
callgrind_annotate cg_base.out | head -40                   # только «своё» время функции
kcachegrind cg_base.out                                      # граф вызовов, картинки в отчёт
```
`bench` гоняет все три сложности, а hard под callgrind будет идти минуты. Поэтому либо мало уровней,
либо (после фикса seed) отдельный режим «только medium».

**Утечки памяти — memcheck** (бонус к отчёту):
```bash
valgrind --leak-check=full ./sokoban_bench 3
```

**Пиковая память — massif** (решатель выделяет десятки МБ):
```bash
valgrind --tool=massif ./sokoban_bench 3 && ms_print massif.out.* | head -40
```

Что записывать в таблицу «исходная версия»: топ-10 функций по inclusive и self (в %),
общее число инструкций (`Ir`), пиковая память, время `bench` без valgrind по сложностям.

## Ключевые термины (English)

- profiling — профилирование, замер, где программа тратит время
- inclusive / self (exclusive) cost — время функции вместе с вызванными / только её собственное
- instruction count (Ir) — число выполненных инструкций, основная метрика callgrind
- hot path / hotspot — горячий путь / горячая точка
- state space — пространство состояний
- admissible heuristic — допустимая эвристика (не завышает оценку)
- open list / closed list — очередь кандидатов / множество уже посещённых состояний
- deadlock (simple / corner / freeze) — тупиковая расстановка ящиков
- dead squares — мёртвые клетки
- push-based search — поиск по толчкам
- loop-invariant code motion — вынос инвариантов из цикла
- strength reduction — замена дорогой операции дешёвой
- precomputation / lookup table — предвычисление / таблица поиска
- cache locality — локальность данных для кэша
- seed — начальное значение генератора случайных чисел
